

# AI Agent Sandbox: Orchestration & Design

This repository provides a deterministic, headless sandbox environment designed for AI agents to interact with the **eShopOnWeb** and **Medplum** projects. It functions as the "Agentic Glue"—the bridge between high-level AI instructions and low-level container infrastructure.

## Quick Start
To spin up a sandbox environment, use the provided orchestration script from the root directory:

```bash
# For eShopOnWeb (SQL Server)
bash projects/scripts/run-sandbox.sh eshop

# For Medplum (PostgreSQL & Redis)
bash projects/scripts/run-sandbox.sh medplum
```

## Design Considerations
I have addressed the core architectural challenges of building a reliable execution environment for AI agents:

### Environment Isolation (One Sandbox or Two?)
I opted for **Isolated Environments**. While both projects are defined in a central `docker-compose.yml`, they are executed as distinct sessions.
*   **Why?** This minimizes memory overhead and prevents "cross-talk" between different database schemas. An AI agent is less likely to hallucinate or fail when it is focused on a single, clean project context.

### Database Strategy
I maintained the native database engines required by each project—**SQL Server 2022** and **PostgreSQL**.
*   **Why?** To ensure that any code or migrations generated by the AI agent are 100% compatible with the project's actual tech stack.

### The "Total Reset" (Clean State)
The sandbox implements a strict "Purge on Exit" strategy using `docker compose down -v`.
*   **Why?** By purging volumes, I ensure every agent run starts with a **mathematically fresh database**. This eliminates "data drift" (leftover data from previous runs) which is a common cause of flaky tests in agentic workflows.

### Headless Automation (Non-interactive Execution)
AI agents cannot "wait" for a service to be ready or click through wizards. I replaced manual wait times with **Automated Health-Check Probes**:
*   **SQL Server:** Polls via `sqlcmd` until the engine accepts a "SELECT 1" query.
*   **PostgreSQL:** Polls via `pg_isready` until the service is live.
*   **The Result:** The script creates a "Sync Gate"—the agent only starts the moment the infrastructure is 100% stable.

### Windows & Cross-Platform Stability
To accommodate Windows host environments (Git Bash), I implemented path-mangling overrides (`MSYS_NO_PATHCONV`) within the orchestration layer.
*   **Why?** This ensures that Linux commands inside the containers (like `/opt/mssql-tools`) don't get broken by Windows file-path translations.

## Summary of Infrastructure

| Feature | Implementation | Benefit |
| :--- | :--- | :--- |
| **Reset Logic** | `docker compose down -v` | Guaranteed fresh data every run. |
| **Health Checks** | `pg_isready` & `sqlcmd` | No manual timing issues or crashes. |
| **OS Compatibility**| `MSYS_NO_PATHCONV` | Reliable execution on Windows/Git Bash. |
| **Structure** | Isolated Containers | Prevents DB conflicts between projects. |

## Output Capture
The sandbox is pre-configured with an `outputs/` directory. The AI agent is expected to write its build logs and test results as **structured JSON** files here. This allows the parent "Harness" to programmatically assess success or failure without parsing raw terminal text.
